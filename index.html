Stacked Pull Requests

Ship in small reviewable pieces — without waiting.

…and let Copilot CLI do the branch plumbing.
20 min + questions. Ask up front: "who has opened a PR over 1000 lines this month?" — hands go up, that's the hook. Promise: one new flag, no new tool to install. Everything is git + gh you already have. Say the live demo is real: 3 open PRs on my GitHub, we'll merge them at the end.

The problem

  • Feature = schema + service + API + tests
  • One PR: 1,400 lines → "LGTM 👍" (nobody read it)
  • Split into 3 PRs off main → PR 2 can't compile without PR 1
  • So you wait. Review latency × 3.
Tell the story, don't read the bullets. Big PR → reviewer opens it, sees 40 files, scrolls, approves. That's not review, that's a rubber stamp. The honest alternative today is splitting off main — but layer 2 doesn't compile without layer 1, so you either wait for merge or you copy commits around. Land the pain point: the bottleneck isn't writing code, it's the serialized wait.

The idea

main
 └─ demo/1-schema  → PR #1 (base: main)
    └─ demo/2-service → PR #2 (base: demo/1-schema)
       └─ demo/3-api   → PR #3 (base: demo/2-service)

Each PR's base is the branch below it →
each PR shows only its own diff.

This is the whole talk in one slide. Pause here. A PR's diff = head compared to its base. Point the base at the branch below instead of main, and GitHub subtracts the parent's changes for you. No tooling, that's just how PRs work. Branch 2 is created FROM branch 1, so it compiles — you keep working while #1 is in review.

Be honest about the last row — it buys credibility. Stacking is not free: feedback on the bottom PR means rebasing everything above it. We'll do exactly that live in demo 3. Reviewers get context in order: schema, then service, then API. They review a story, not a pile. Revert row: if the API layer is broken in prod you revert one squash commit, not the whole feature.

Demo 1 — build the stack

Create a throwaway private repo stacked-pr-demo, clone it, and build a 3-PR stack for a fake price feature: branch demo/1-schema (schema.sql) based on main, demo/2-service (service.java) based on demo/1-schema, demo/3-api (controller.java) based on demo/2-service. Push each and open a PR with gh pr create -B <parent branch>, titled "1/3 …", "2/3 …", "3/3 …". Print the 3 PR URLs.
Read the prompt out loud — the point is that it's plain English, no git jargon. Notice I never say "rebase" or "checkout -b". If you're running Copilot live: paste it and let it work while you talk over the next slide. If the room's wifi is bad, skip to the commands slide, it's the same thing. Note "throwaway private repo" — make it public before the talk or the links on the demo slide 404 for the audience.

…what it actually runs


gh repo create stacked-pr-demo --private --clone && cd stacked-pr-demo
echo "# demo" > README.md
git add -A && git commit -m "init" && git push -u origin main

git checkout -b demo/1-schema
echo "CREATE TABLE price(id int primary key);" > schema.sql
git add -A && git commit -m "add price schema"
git push -u origin demo/1-schema
gh pr create -B main -H demo/1-schema -t "1/3 price schema" -b "Base: main"

git checkout -b demo/2-service           # branches off 1-schema
echo "class PriceService {}" > service.java
git add -A && git commit -m "add price service"
git push -u origin demo/2-service
gh pr create -B demo/1-schema -H demo/2-service -t "2/3 price service" -b "Base: #1"

git checkout -b demo/3-api               # branches off 2-service
echo "@RestController class PriceController {}" > controller.java
git add -A && git commit -m "add price API"
git push -u origin demo/3-api
gh pr create -B demo/2-service -H demo/3-api -t "3/3 price API" -b "Base: #2"

The only trick: -B <parent branch>.

Don't read the script line by line — highlight three things only: 1) each `git checkout -b` runs while the previous branch is checked out, so branch 2 contains branch 1's commits; 2) `gh pr create -B demo/1-schema` — that's the whole feature, every other flag is normal; 3) titles numbered 1/3, 2/3, 3/3 so reviewers know the order. Everything else is `echo` and `commit` to fake a feature.

Demo 2 — prove it's stacked

For each PR in stacked-pr-demo, show its base branch and the files it changes, so I can demo that each PR only contains its own diff.
Short slide. This is the "prove it" moment — people are skeptical that GitHub really hides the parent's diff. Say what you expect BEFORE running it: "PR 3 should show one file, controller.java, even though the branch contains three commits." 

gh pr list --json number,title,baseRefName,headRefName
gh pr view 2 --json files --jq '.files[].path'   # only service.java

Open PR #2 in the browser → "Files changed: 1"

Actually switch to the browser here — the "Files changed: 1" badge next to a 3-commit branch is what sells the whole idea. Also point at the base-branch dropdown at the top of the PR: `demo/2-service ← demo/3-api`. That dropdown is the entire feature. Expected question: "does CI run on these?" — yes, normally; each PR builds its own branch, which contains the parents, so it compiles.

Demo 3 — feedback on the bottom PR

The one real cost of stacking.

Simulate review feedback on PR #1: add a NOT NULL column to schema.sql, commit and push to demo/1-schema, then restack demo/2-service and demo/3-api on top with git rebase + git push --force-with-lease. Show me the commands as you run them.
Set it up as the objection: "fine, but what happens when a reviewer wants a change in PR 1?" This is the part people worry about, so don't hide it. This is also where Copilot earns its keep — the rebase chain is mechanical, error-prone, and boring. Exactly the work to hand off. Say "show me the commands as you run them" is deliberate: for a talk you want the commands visible, not just the result. 

git checkout demo/1-schema
echo "ALTER TABLE price ADD COLUMN gross numeric NOT NULL;" >> schema.sql
git commit -am "review: gross not null" && git push

# restack, bottom-up
git rebase demo/1-schema demo/2-service
git push --force-with-lease
git rebase demo/2-service demo/3-api
git push --force-with-lease

Always --force-with-lease, never bare --force.

Two things to stress: 1) Restack BOTTOM-UP. Rebase 2 onto 1 first, then 3 onto the new 2. Do it top-down and you'll rebase onto commits that are about to be rewritten. 2) `--force-with-lease` aborts if someone else pushed to that branch in the meantime; plain `--force` silently overwrites their work. On a stack you force-push constantly, so make it muscle memory. Honest caveat: existing review comments on the rebased PRs can go "outdated" — that's the real tax. Keep stacks 3–4 deep so it stays cheap. Conflicts: resolve once, at the layer that owns the file; `git rebase --continue` and move up.

Demo 4 — merge cascade

Merge PR #1 with squash, then show the base branch of PRs #2 and #3 so I can demo GitHub's auto-retargeting. Then merge #2, re-check #3, then merge #3.
The payoff slide. Most people assume unwinding a stack is manual work — it isn't. Ask the room first: "when I merge #1 and delete its branch, what happens to #2, whose base was that branch?" Usual guess: it closes or breaks. It doesn't. 

gh pr merge 1 --squash --delete-branch
gh pr view 2 --json baseRefName   # -> "main"   ← GitHub retargeted it
gh pr merge 2 --squash --delete-branch
gh pr view 3 --json baseRefName   # -> "main"
gh pr merge 3 --squash --delete-branch

Merge bottom-up. GitHub retargets the child automatically — no manual base editing.

Run the `gh pr view 2 --json baseRefName` line and let the output speak: base flipped from demo/1-schema to main by itself. Caveat worth naming: squash-merge rewrites history, so after merging #1 you may need one more rebase of #2 onto main before it's clean. On a small demo it just works; on a real stack, expect one restack per merge. Alternative if that annoys you: merge-commit instead of squash. We prefer squash for a readable main — pick one and be consistent.

Rules of thumb

  • Merge bottom-up, always.
  • Number your titles 1/3, 2/3, 3/3 and link the parent in the body.
  • Keep the stack ≤ 3–4 deep. Deeper = rebase pain > review win.
  • Rebase, don't merge, when restacking.
  • Squash-merge keeps main readable.
The "what do I do tomorrow" slide — slow down, this is what they'll remember. Depth limit is the important one: 3–4. Beyond that the rebase chain costs more than the smaller reviews save. Add: split by layer, not by file count — each PR should be independently reviewable and ideally independently green. And: tell your reviewer it's a stack. A reviewer who doesn't know will ask "where's the API for this schema?"

Takeaway

Stacked PRs = small reviews without blocking yourself.

Plain git + gh is enough — the only new flag is gh pr create -B <parent>.

Copilot CLI handles the branch/rebase plumbing so you can stay on the feature.
Close with the ask, not a summary: "next feature that's more than ~300 lines, split it into two stacked PRs. Just two. Tag me as reviewer and I'll help." Deck + prompts are shareable: link in the channel. Likely questions: • "Do we need Graphite / git-spr?" — No. Useful if you stack daily; plain gh is enough to start. • "What about branch protection / required reviews?" — applies per PR as usual; merge bottom-up and each gets its own approval. • "Isn't force-pushing dangerous?" — only on shared branches; a stack branch is yours, and --force-with-lease protects you. • "What if the stack goes stale vs main?" — rebase the bottom onto main, then restack upward. Same drill as demo 3.
